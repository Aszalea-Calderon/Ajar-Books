# 0002. Never write to an app database file except through the running app itself

**Status:** Accepted

**Update 4 (2026-08-06, same day) — the actual definitive fix:** a fifth incident happened after Update 3's singleton fix was already in place and verified (confirmed only one connection open, no leak), through completely normal `pnpm dev` use with no raw scripts involved at all. This meant the singleton fix, while a real improvement, wasn't the full story. The common thread across all five incidents — a Docker/host bind mount, a raw script racing a live server, a leaked dev-mode connection, a container killed mid-checkpoint, and finally a single well-behaved connection — is `journal_mode = WAL` itself: every one of these failure modes traces back to WAL's requirement that every connection touching the file correctly coordinate through a shared `-shm` index. **Fixed by dropping WAL mode entirely**, in favor of SQLite's default rollback-journal mode, which has no shared-memory coordination to get wrong. This app is single-user with no real concurrent-write workload, so WAL's one actual benefit (readers not blocking a writer) was never buying anything here — it was pure downside. See `src/lib/server/db/index.ts`. Verified with a harder stress test than Update 3's: 8 cycles of editing `db/index.ts` itself (the most direct test possible) plus other server files, each followed by a real request, with book count checked every cycle — held steady throughout. The rules below (separate dev/Docker files, never raw-script a live file, careful container restarts) are still good practice and stay documented, but the actual bug is fixed, not just mitigated.

**Update (2026-08-06, same day):** the mechanism is broader than first diagnosed below. A second, separate incident happened on `local.db` alone — no Docker involved, a single local dev server process, seeded via a raw `better-sqlite3` script while that dev server was running. Same symptom: data collapsed back down to ~1 row per table. The common factor across both incidents isn't specifically the Docker/host virtualization boundary — it's **any second process or script writing to a SQLite file that a live server connection already has open**, even fully local, same machine, same filesystem. The original Docker/WAL analysis below is kept as the first incident's record, but the actual rule is broader — see Decision, updated.

**Update 3 (2026-08-06, same day) — actual root cause found and fixed:** a fourth incident (same collapse symptom as #1/#2, not corruption like #3) happened on `local.db` with zero raw scripts involved at all — just normal `pnpm dev` usage while iterating on shelf code. This pointed at the real root cause of incidents 1, 2, and 4 (incident 3's corruption was a separate, compounding issue, see below): `src/lib/server/db/index.ts` opened a new `better-sqlite3` connection and ran `migrate()` as **module-level side effects**. Vite's dev-mode SSR module invalidation re-executes a module's top-level code on requests after editing files in its dependency graph — which, across a long session touching many server files, re-ran this module dozens of times, each time opening a fresh WAL connection without ever closing the previous one. Multiple leaked WAL connections to the same file, all within one process, is what actually caused the repeated data collapses.

**Fixed** by caching the connection on `globalThis` (which survives module re-evaluation, unlike the module's own top-level scope) so exactly one connection and one `migrate()` call happen per real process lifetime, in dev or prod. Verified by stress-testing the exact failure pattern — repeatedly editing server files and hitting the app between edits — with the fix in place; book count stayed correct across 10 cycles where it previously would have collapsed. See `src/lib/server/db/index.ts`.

This means the Docker/host-boundary write and the raw-script-while-server-running rules below are still worth following (defense in depth, and incident 3's corruption was real and separate), but they were treating a symptom — the actual bug was in this app's own code, and is now fixed.

**Update 2 (2026-08-06, same day):** a third incident, worse than the first two — `docker compose up -d` recreating the container (to pick up new code) stopped the old container while its WAL had a large pending checkpoint (~4MB, same pattern as the earlier incidents), and it appears to have been killed mid-checkpoint. Result: `data/ajar-books.db`'s header was corrupted badly enough that `sqlite3`/`PRAGMA integrity_check` couldn't even open it as a database (`SQLITE_NOTADB`) — not just data loss, file-level corruption, with the `-wal`/`-shm` companions gone entirely. Recovered by moving the corrupted file aside (`data/corrupted-backup/`) and letting a fresh container create a new empty database, then re-importing from the source CSV (which was never touched, so nothing was actually unrecoverable this time). **New rule: before recreating/restarting a running container, prefer `docker compose down` (a real stop, waited-for) over relying on `up -d`'s implicit recreate**, and be aware a container with a large pending WAL is a real risk during shutdown regardless of method — this app doesn't yet have any signal handling to force a checkpoint before exit.

## Context

On 2026-08-06, while doing local development work (`pnpm dev`), `.env`'s `DATABASE_URL` was pointed at `data/ajar-books.db` — the same path `docker-compose.yml` bind-mounts (`./data:/app/data`) into a long-running Docker container that had been up for 28 hours. Both processes opened the same SQLite file in WAL mode at once: one on the host, one inside Docker Desktop's Linux VM, coordinating over a bind-mounted volume.

The result was a near-total data loss: the real database (446 books, full reading history, 423 library entries) collapsed to roughly 1 row per table. This was confirmed genuine (not a stale read) by force-checkpointing the WAL and re-querying — same reduced state, on both the host file and inside the container. No backup existed to recover from. In this case the lost data turned out to be test data the user hadn't treated as precious yet, so the practical impact was low — but the failure mode itself is real and would be serious against genuine data.

**Root cause:** SQLite's WAL mode depends on shared-memory (`-shm`) locking between every process with the file open, to coordinate reads/writes/checkpoints. This is a well-documented weak point across the host/container boundary Docker Desktop for Mac uses for bind mounts — the two sides don't reliably share that locking, so concurrent WAL writers on each side can each believe they hold consistent state while actually clobbering each other's writes or checkpoints.

## Decision

Two separate rules, both required:

1. **Local dev (`pnpm dev`) and the Docker-deployed instance must never point at the same SQLite file**, ever, even briefly. `.env`'s `DATABASE_URL` for local dev is `local.db` — a dev-only file, safe to delete/recreate at any time, never the same path Docker's `./data` volume uses. Before starting `pnpm dev`, check `docker ps` for a running container from this project; if one is up, local dev must use its own separate database file regardless of what `.env` currently says.
2. **Never write to any app database file with a raw script (`sqlite3`, a one-off `better-sqlite3` script, etc.) while a server process — `pnpm dev` or the Docker container — already has that same file open.** Confirmed by the second incident: this broke `local.db` even with no Docker involved, single machine, single filesystem, just a live dev server plus a separate short-lived write connection. To seed or modify data, either (a) go through the running app's own routes — its Import wizard, form actions, `POST` endpoints — driven via a real browser session (Playwright, or by hand), or (b) stop every process that has the file open first, then use a raw script, then restart.

`pnpm test` is unaffected by either rule — it already runs against `DATABASE_URL=':memory:'` (set in `vite.config.ts`'s vitest config), fully isolated, never touches a file on disk.

Both rules are recorded in `CLAUDE.md` as standing warnings.

## Alternatives considered

- **Always stop the Docker container before running `pnpm dev`, keep one shared `DATABASE_URL`** — works, but relies on remembering to stop/restart Docker every time, and still uses the real file as a dev sandbox, risking exactly this failure the moment someone forgets. Rejected in favor of structurally separate files, which makes the mistake impossible rather than just avoidable.
- **Switch the app to a WAL-safe multi-process setup (e.g. a network-accessible DB, or disabling WAL)** — over-scoped for a single-user self-hosted app; the actual problem is two *development* processes racing on one file, not a real need for the production app itself to support concurrent multi-process access.

## Consequences

- `local.db` is never a source of truth and is safe to delete freely — a fresh one plus a re-import/re-seed is always the recovery path if it gets into a bad state.
- Any future tooling or scripts that read `DATABASE_URL` from `.env` should assume it may point at either file depending on context, and must not assume "the database" always means the real one.
- If this project ever needs local dev to run against a live-shared database on purpose (not the case today), that would need a real multi-process-safe setup, not just pointing two dev tools at the same SQLite file.
