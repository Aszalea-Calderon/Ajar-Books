# Ajar Reads — Build Roadmap

_Phased build order with checklists. Estimates assume part-time, evenings/weekends pace with Claude Code as an active pair-programmer — treat them as rough planning ranges, not commitments._

**One ordering note:** Import (Phase 3) is sequenced _before_ the streak calendar and Insights, not after — importing your real reading history early gives Phases 4 and 5 real data to build and test against, instead of a handful of manually-entered test books.

## Phase 0 — Foundation

**Why this order:** everything else depends on a working, deployable skeleton. Getting `docker compose up -d` → login working end-to-end early means deployment problems surface now, not after months of feature work.
**Estimate:** 2-4 sessions

| Done | Task                                                                                |
| ---- | ----------------------------------------------------------------------------------- |
| ☑    | Initialize SvelteKit project                                                        |
| ☑    | Write Docker Compose setup (single container)                                       |
| ☑    | Wire up SQLite + Drizzle ORM (schema + migrations)                                  |
| ☑    | Build first-run account creation flow (not open signup)                             |
| ☑    | Build sign-in screen                                                                |
| ☑    | Build empty dashboard shell/layout                                                  |
| ☑    | Set up base design-token architecture (CSS custom properties, one default theme)    |
| ☑    | Verify: clone → `docker compose up -d` → create account → see dashboard, end to end |

_Incident (2026-08-06):_ running `pnpm dev` with `DATABASE_URL` pointed at the same `data/ajar-books.db` file a live Docker container had open caused a near-total data loss (446 books/full history collapsed to ~1 row per table) — SQLite's WAL mode doesn't reliably coordinate locking across the host/container boundary Docker Desktop for Mac uses for bind mounts. No backup existed; the lost data happened to be test data, so impact was low, but the failure mode is real. Fixed by permanently separating dev (`local.db`) from Docker's real data path, documented in [CLAUDE.md](CLAUDE.md) as a standing warning and in [docs/adr/0002-separate-dev-and-docker-databases.md](docs/adr/0002-separate-dev-and-docker-databases.md) as the full incident record and decision.

_Incident 2 (2026-08-06, same day):_ recurred on `local.db` alone — no Docker involved — when a raw `better-sqlite3` seed script wrote to `local.db` while `pnpm dev` was already running against it. Same collapse symptom. This showed the real rule is broader than the Docker/host boundary: any second process/script writing to a SQLite file a live server connection already has open is unsafe here. Fixed by reseeding through the app's own Import wizard instead (driven via a real browser session) rather than a raw script, and broadened both `CLAUDE.md` and ADR 0002 accordingly.

_Incident 3 (2026-08-06, same day):_ worse than the first two — `docker compose up -d` recreating the container to pick up new code stopped the old container mid-WAL-checkpoint, corrupting `data/ajar-books.db`'s header badly enough that SQLite couldn't open it at all (not just data loss). Recovered by moving the corrupted file aside and starting fresh, since the source CSV was untouched. New rule added to `CLAUDE.md`/ADR 0002: prefer `docker compose down` (a real, waited-for stop) before rebuilding, since this app has no shutdown signal handling to force a checkpoint before exit — that's the actual underlying gap worth fixing properly (see Fix List).

_Incident 4 (2026-08-06, same day):_ recurred on `local.db` a third time, this time with zero raw scripts involved — just normal `pnpm dev` use while iterating on the 3D shelf. Traced (at the time) to `src/lib/server/db/index.ts` opening its SQLite connection and running `migrate()` as module-level side effects, which Vite's dev-mode HMR silently re-executes on requests after editing server files — leaking a new WAL connection every time without closing the old one. Fixed by caching the connection on `globalThis` so it's created exactly once per process. This turned out to be a real improvement but not the full fix — see Incident 5.

_Incident 5 (2026-08-06, same day) — actual definitive fix:_ happened again after the singleton fix above was verified working (confirmed only one connection open, no leak), through completely normal use with nothing unusual going on. This made the real common thread across all five incidents obvious: `journal_mode = WAL` itself. Every failure mode — Docker/host bind mount, raw script vs. live server, leaked connection, container killed mid-checkpoint, and now a single well-behaved connection — traces back to WAL requiring every connection to correctly coordinate through a shared `-shm` index. **Fixed by dropping WAL mode entirely**, using SQLite's default rollback-journal instead, which has no shared-memory coordination to get wrong. This app is single-user with no concurrent-write workload, so WAL's one real benefit was never buying anything here. Verified with a harder stress test than Incident 4's: 8 cycles of editing `db/index.ts` itself (the most direct test possible) plus other server files, each followed by a real request — book count held steady throughout. Full writeup in ADR 0002 ("Update 4"). The Docker-boundary and raw-script rules from incidents 1–4 are still good practice and stay documented, but the actual bug is fixed now, not just mitigated.

_Why we won't do local/offline search as of now:_ it's the only way to get to zero third-party exposure on searches (Open Library never sees a query at all if you're not sending one), but it's a lot of infrastructure for what is, in this app's threat model, public book-metadata lookups rather than sensitive data. Concretely: Open Library's bulk dumps (works/editions/authors) run to tens of GB, need a real full-text index to be searchable at speed (SQLite's own `FTS5` extension at minimum), go stale between refreshes (a book released after your last sync won't appear until the next one), and still leave cover images as a separate hot-linking-vs-bulk-download problem of their own. That's a meaningful ongoing maintenance burden for a single-user hobby app, not a one-time cost.

_How to build it yourself, if you want it sooner:_

1. Download the bulk dumps from [openlibrary.org/developers/dumps](https://openlibrary.org/developers/dumps) (`works`, `editions`, `authors` — each a large gzipped TSV).
2. Parse and import them into a local search index — e.g. a SQLite `FTS5` virtual table alongside the existing `books` table, or a dedicated embedded search engine if `FTS5` turns out too slow at this record count.
3. Build a scheduled job (cron, or a simple background task in the app) to re-download and re-import the dumps periodically — monthly matches Open Library's own dump cadence — with a clean diff/replace so stale rows don't linger.
4. Add a choice at onboarding (or in Settings) — "Live search" vs. "Local search (larger download, refreshes monthly)" — store it in the `settings` table, and branch `searchBooks()` in `search.ts` to either the existing live-API path or a new local-index query based on it.
5. Decide what to do about cover images in local mode: keep hot-linking `covers.openlibrary.org` (a small, separate privacy leak limited to image requests, not search terms) or bulk-download a cover cache too (meaningfully more storage).
6. Surface the storage/staleness tradeoff clearly at the point of choice, so picking "local" is an informed decision rather than a surprise disk-usage spike later.

Surfaced 2026-08-21 with a question about applying Signal Protocol techniques — worth being explicit that Signal's Double Ratchet/X3DH solve a different problem (two live parties exchanging messages through an untrusted relay, with forward secrecy across sessions); this app is one user and one self-owned server, so there's no relay/second-party to protect against, and no Double Ratchet to borrow.
